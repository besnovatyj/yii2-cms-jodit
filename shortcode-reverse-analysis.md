# Анализ выборочного обратного преобразования текстовых шорткодов

Дата анализа: 2026-11-14.
Статус: материал для замечаний и последующего составления плана работ. Изменения реализации не выполнялись.

## Задача и границы

Файловый менеджер вставляет публичные URL вида:

```text
https://files.yii2-cms.docker.localhost/origin/Blog/502/123.jpg
```

В сохраняемом контенте требуется получать:

```text
%staticHost%/origin/Blog/502/123.jpg
```

В WYSIWYG должны использоваться реальные адреса, а в исходном коде и сохраняемом HTML — шорткоды. Обратное преобразование разрешается только явно выбранным текстовым шорткодам. Например, `%homeUrl%` со значением `/` не должен участвовать в обратной замене.

Имена шорткодов и их правила не должны быть захардкожены в репозитории редактора. Файловый менеджер продолжает возвращать публичные URL и не получает зависимости от шорткодов. Виджетные шорткоды в эксперимент не входят.

## Общий вывод

Решение реализуемо без хардкода шорткодов в Jodit и без изменений файлового менеджера. Но отсутствие конфликтов подтвердить нельзя: в текущем коде есть несколько несогласованностей, которые необходимо устранить вместе с внедрением обратной замены. Простого добавления поля `reverse` недостаточно.

Проверены хранение, регистрация, API, потребители шорткодов, интеграция редактора, исходники установленного Jodit **4.15.14**, сохранение контента и представления, которые его выводят.

## 1. API и серверная подстановка могут использовать разные значения одного шорткода

В `../yii2-cms-shortcode/src/components/ShortcodeManager.php`, в `init()`, встроенные значения накладываются поверх записей БД. Например, для `%staticHost%` побеждает значение из параметров приложения.

В `../yii2-cms-shortcode/src/readModels/ShortcodeListReadModel.php`, в `all()` и `appendRuntime()`, приоритет противоположный: запись из БД сохраняется, одноимённая runtime-регистрация пропускается.

Следствие: редактор потенциально показывает один адрес, а frontend подставляет другой. С обратной заменой расхождение затронет ещё и сохранение.

Нужен единый реестр **эффективных определений шорткодов**. Он должен одинаково определять имя, тип, значение и правило обратного преобразования для API и серверного рендера. Правило нельзя объединять отдельно от значения: они должны принадлежать одному определению.

Рекомендация: запретить дублирование встроенных имён в БД. Для остальных источников явно определить порядок регистрации и обработку конфликтов.

> Я бы не запрещал дублирование, а сделал так чтобы значения из базы переопределяли всё остальное. В принципе маловероятно что это вообще когда-то произойдёт, но для подстраховки можно так сделать. В итоге админка получит всю полноту власти над определениями и переопределениями шорткодов. Например, где-нибудь в php коде определён шорткод статики разрешеющий reverse замену, а админ переопределив шорткод в базе данных запретит reverse. Навряд ли это произойдёт, но для чистоты архитектуры вполне себе красивая логика. По поводу единого реестра - предложи своё видение архитектуры

## 2. Runtime-регистрации сейчас не гарантированно видны API

`ShortcodeListReadModel` получает `ShortcodeManager` через конструктор. Компонент `Yii::$app->shortcode` создаётся отдельно. Общего экземпляра менеджера текущая конфигурация DI не обеспечивает.

Поэтому вызов:

```php
Yii::$app->shortcode->registerText(...);
```

не гарантирует, что регистрацию увидит менеджер, внедрённый в API или `ShortcodeContent`.

Общий кэш БД эту проблему не решает: runtime-регистрации находятся в памяти конкретного объекта.

В `../yii2-cms-shortcode/src/config/common.php` уже описана рекурсия при попытке напрямую связать класс менеджера с компонентом приложения. Эту оговорку необходимо сохранить и учесть.

Архитектурное решение — отдельный общий реестр определений, используемый менеджером и read model. При этом регистрации должны выполняться и в запросе API: регистрация только во время построения формы не переживёт переход в отдельный HTTP-запрос загрузки шорткодов.

Но, нужен анализ yii2, я не очень хорошо знаю его внутреннюю реализацию. Поиск в `vendor/besnovatyj` строки `'singletons' =>` может помочь найти файлы, где есть рабочие примеры работы с контейнером в приложении 

## 3. Прямая подстановка в браузере и PHP уже различается

В `assets/plugins/shortcodes.ts`, в `applyReplacements()`, замены выполняются последовательно. В PHP `ShortcodeManager::resolveText()` делает один проход по исходной строке.

Например:

```text
%a% → %b%
%b% → значение
```

Для `%a%` браузер может получить `значение`, а PHP — `%b%`. Результат браузера также зависит от порядка элементов.

Это подтверждено выполнением существующей функции плагина в памяти.

Нужно согласовать семантику прямой подстановки. Рекомендация: один проход без каскадного раскрытия. Для обратимых URL-правил значение дополнительно должно быть конечным абсолютным HTTP(S)-адресом, без вложенных шорткодов.

> Поддерживаю, никакие вложенности и каскадные раскрытия не нужны. Шорткоды шорткодов это перебор, никто и никогда в этом не разберётся. Система шорткодов это упрощение работы, а не усложнение. Значение шорткода это всегда готовый результат для фронтэнда.

## 4. Механизм Jodit подходит, но загрузку правил необходимо включить в жизненный цикл редактора

В установленной версии Jodit и исходник, и синхронизация textarea используют `getEditorValue()`. Событие `afterGetValueFromEditor` подходит для получения HTML с шорткодами.

Проводник вызывает `insertImage()` или `insertHTML()`, которые запускают синхронизацию. Поэтому отдельная связь проводника с плагином шорткодов не нужна.

Проверенные исходники Jodit:

- `node_modules/jodit/esm/jodit.js`;
- `node_modules/jodit/esm/plugins/source/source.js`;
- `node_modules/jodit/esm/core/selection/selection.js`.

Однако сейчас после загрузки списка `attachShortcodePreview()` только декорирует DOM. Повторная синхронизация textarea не выполняется. Это также подтверждено проверкой существующего кода.

Необходимо обеспечить:

- применение правил к уже открытому контенту;
- обновление выходного значения после загрузки;
- корректную работу при открытии сразу в source или split;
- защиту от выполнения асинхронного обработчика после уничтожения редактора.

Есть и принципиальное ограничение: **пока правила не загрузились, редактор не может выполнить обратную замену**. При ошибке API действующий код продолжает работу без шорткодов.

Если требуется строгая гарантия «домен никогда не попадёт в БД», одной клиентской обработки недостаточно. Нужна либо обязательная готовность правил перед сохранением, либо дополнительная серверная нормализация через общий сервис модуля шорткодов. Это отдельное требование к сохранению, которое нельзя обещать автоматически.

> Я думал над серверной работой с шорткодами. Но, мне кажется, это может чрезмерно усложнить общую логику. Мне нравится подход когда я могу видеть в редакторе в режиме исходника именно то что улетит в базу данных. Серверное преобразование перед сохранением или при получении из базы данных - это почти магия, не совсем, но почти. Такие подходы тоже допустимы, но они должны явно представлять архитектуру приложения - например, если мы в качестве транспорта от бэкэнда до браузера используем JSON - тогда магии нет. А вот если мы меняем на сервере автоматически кусок строки в тексте, а администратор в админке этого может не знать, очень скоро получится ситуация когда сохраняешь в админке одно, а при попытке повторного редактирования открывается другое. Это слишком неоднозначный способ работы с контентом, который требует дополнительных проверок для устранения багов несогласованности. Лучше уж пусть строка домена проскользнёт в базу, чем мы породим глобальную точку несогласованности, лучше получить один сломанный пост, чем сломанную логику всего приложения. Но, замечу, что алерт с ошибкой доступности API шорткодов поверх редактора вполне допустим. Все ошибки должны быть явные. Явная ошибка и блокировка работы это путь к быстрой починке - если Jodit позволяет своему плагину подобное поведение, то это и может быть решением проблемы.   

## 5. Нельзя смешивать восстановление исходного шорткода и создание нового

Сейчас `restore()` в `assets/plugins/shortcodes.ts` восстанавливает значения только по служебным меткам. Если меток нет, HTML сразу возвращается без обработки.

Для обратной замены нужны две последовательные операции:

1. Восстановить существующие шорткоды по меткам, сохранив нынешнюю проверку изменения атрибута.
2. Преобразовать подходящие реальные URL по разрешённым правилам.

Уже существующий шорткод следует сохранять, даже если его значение совпадает со значением другого шорткода. Иначе редактор начнёт самовольно менять авторский выбор.

История Jodit хранит копию DOM, а не результат `afterGetValueFromEditor`. Это проверено в `node_modules/jodit/esm/modules/history/snapshot.js`. Следовательно, undo/redo должно отдельно проверяться с превью и метками. Само преобразование выходного HTML не должно создавать дополнительные шаги истории.

## 6. Правило url-prefix требует строгого определения

Обратная подстановка неоднозначна по своей природе: несколько шорткодов могут иметь одинаковое значение. Поэтому необходимы правила разрешения конфликтов:

| Ситуация | Предлагаемое поведение |
|---|---|
| Обратное преобразование отключено | Значение не участвует в поиске |
| Значение `/`, пустая строка или относительный путь | Недопустимо для `url-prefix` |
| Несколько подходящих префиксов | Выбирается наиболее длинный |
| Одинаковые префиксы у разных разрешённых шорткодов | Ошибка конфигурации |
| В URL уже есть шорткод | Существующая запись сохраняется |
| Неизвестный режим из API | Правило не применяется |

Сопоставление должно учитывать границы адреса и пути. Нельзя заменять `https://files.example.com` внутри `https://files.example.com.evil/a.jpg` или `/media` внутри `/media-old`.

Также нельзя бесконтрольно пересобирать URL: файловый менеджер уже кодирует сегменты пути в `../yii2-cms-file/src/fs/mount/url/BaseUrlResolver.php`. Нужно сохранять закодированные имена файлов, query string и fragment.

Отдельное ограничение: правило с текущим доменом не распознает старый домен после переезда. Если потребуется такая возможность, старые адреса должны задаваться как явные дополнительные префиксы в модуле шорткодов.

> Переезд между доменами это всегда работа с именами доменов через сырой SQL, никакие WYSIWYG редакторы об этом не знают. Да и вообще, если мы изначально используем шорткоды, то в базе данных не будет доменов, там будут только шорткоды.

## 7. HTML-контекст должен оставаться ответственностью интеграции Jodit

Текущее превью обрабатывает только `src`, `srcset`, `poster`. Для файловых ссылок необходимо добавить `href`, причём согласовать и прямую, и обратную обработку.

`srcset` требует отдельного разбора адресов и дескрипторов. Простое разбиение по запятым некорректно для всех допустимых значений.

Обрабатывать весь HTML строковой заменой нельзя. Текст статьи, CSS, скрипты и текстовый синтаксис виджетных шорткодов должны оставаться вне этого механизма.

При действующих настройках очистки Jodit явного запрета на необходимые атрибуты и метки не обнаружено. Пользовательские `cleanHTML.allowTags` или собственный sanitizer могут изменить ситуацию — это необходимо покрыть проверкой интеграции.

Проверены:

- `node_modules/jodit/esm/plugins/clean-html/config.js`;
- `node_modules/jodit/esm/plugins/clean-html/clean-html.js`;
- `node_modules/jodit/esm/core/helpers/html/safe-html.js`;
- `node_modules/jodit/esm/plugins/clean-html/helpers/visitor/visit-node-walker.js`.

## 8. Глобальная автозамена затронет представления, которые пока не поддерживают шорткоды

Это самый существенный конфликт за пределами двух плагинов.

Редактор используется в блоге, страницах, каталоге, персонах, галереях, сниппетах и других формах. При этом обработка сохранённого HTML неодинакова:

- `/app/themes/berdrama/modules/Blog/views/frontend/post/view.php` использует `ShortcodeContent`.
- `../yii2-cms-blog/src/views/frontend/post/view.php` выводит `$post->content` напрямую.
- `../yii2-cms-catalog/src/views/frontend/product/item.php` передаёт описание в HTML-форматтер без явного раскрытия шорткодов.

Поэтому включить автозамену сразу во всех редакторах сейчас нельзя считать безопасным: часть представлений получит буквальный `%staticHost%` в адресах.

Необходим единый подход к обработке таких полей при выводе. Для текстовых подстановок уже существует подходящий узкий контракт `../yii2-cms-contracts/src/shortcode/ShortcodeTextResolver.php`; зависимость всех потребителей от конкретного `ShortcodeContent` не требуется. При использовании HTML-очистки раскрытие URL нужно согласовать с её порядком.

> Здесь моя недоработка в структуре файлов "AGENTS.md", не ищи сейчас это правило, но в папке vendor у всех модулей только базовые представления для понимания логики работы модуля, эти представления не используются непосредственно в работе приложения. Приложение всегда работает через темизацию, если на фронт попало исходное представление модуля, то это баг, я за этим слежу и не допускаю подобного. А поскольку я не хочу в зависимости каждого контентного модуля добавлять шорткоды, модули и не используют преобразования шорткодов. Да, можно сделать еще один уровень абстракции, добавить контракты, но я не хочу - модули не знают про шорткоды, про шорткоды знает тема и программист. Пока это можно считать техническим долгом или отслеживаемым осознанным упрощением.   

## 9. Хранение reverse укладывается в существующую структуру

Предложение: хранить конкретный режим в поле `reverse_mode`, представленном в PHP типизированным значением. Для текущей задачи достаточно состояний «отключено» и `url-prefix`; произвольный JSON в БД не требуется.

Изменения проходят по существующей цепочке:

```text
Миграция → сущность → форма → сервис сохранения
→ каталог/реестр → read model → API → плагин Jodit
```

Для программных определений политика передаётся при регистрации. Для `%staticHost%` она задаётся в модуле шорткодов рядом с его определением. Для `%homeUrl%` остаётся отключённой.

Потребуются валидация режима, запрет правила для виджетного типа и проверка конфликтов всего эффективного реестра.

Механизм `../yii2-cms-modman/src/migration/ModuleMigrationRunner.php` поддерживает добавление новой миграции при обновлении. Старую установочную миграцию менять не нужно. Новая миграция должна наследовать `../yii2-cms-kernel/src/migration/BaseMigration.php`.

Кэш также требует внимания:

- старые записи APCu не содержат нового поля — нужна совместимость формата либо смена ключа;
- браузерный кэш сейчас хранит список до перезагрузки страницы;
- параллельные загрузки не объединяются в один запрос;
- API-ответ сейчас проверяется лишь на наличие массива, без проверки структуры элементов.

### Разделение ответственности

| Ответственность | Владелец |
|---|---|
| Какой шорткод допускает обратную замену и по какому правилу | Модуль шорткодов |
| Какие HTML-атрибуты содержат URL и как их обрабатывать | Интеграция шорткодов в Jodit |
| Получение публичного URL файла | Файловый менеджер |

Список HTML-атрибутов не должен храниться в определении шорткода. Знание про `srcset`, `href` и DOM относится к редакторной интеграции.

Пример предполагаемого представления в API:

```json
{
  "shortcode": "%staticHost%",
  "type": "text",
  "replacement": "https://files.yii2-cms.docker.localhost",
  "reverse": {
    "mode": "url-prefix"
  }
}
```

Это формат передачи данных, а не конфигурация конкретного шорткода в репозитории Jodit. Редактор реализует общий алгоритм и не содержит конкретных имён.

Для шорткодов из БД режим правится в форме управления шорткодом. Для программных определений источником настройки остаётся код регистрации. Редактирование программных определений через админку, если потребуется, должно быть отдельно оформлено как механизм сохраняемых переопределений.

## 10. Опциональность сохраняется, но сейчас включение интеграции не автоматическое

У пакета Jodit нет обязательной Composer-зависимости от модуля шорткодов — это соответствует задуманной архитектуре.

Однако `JoditWidget::$enableShortcodes` по умолчанию равен `true`, а наличие модуля перед формированием URL API не проверяется. При его отсутствии редактор продолжает работать после ошибки загрузки, но кнопка и запрос остаются.

Для чистой установки интеграция должна включаться по доступности поставщика шорткодов с возможностью явного переопределения URL. Конкретные имена шорткодов при этом редактору по-прежнему не нужны.

Отключение модуля на чистой установке и отключение на сайте с уже сохранёнными шорткодами — разные случаи: во втором случае существующий контент требует работающего резолвера.

> Согласен, это плохо и нелогично, но пока оставим как есть, займусь этим позже, и так много работы сейчас будет.

## Рекомендуемая архитектура после проверки

**Модуль шорткодов владеет определениями и политикой обратной замены; плагин Jodit владеет HTML-обработкой; проводник возвращает публичные URL.**

Внедрение должно включать единый реестр, согласованную прямую подстановку, валидацию обратимых правил, корректную асинхронную инициализацию редактора и согласование вывода полей, где появятся автоматические шорткоды.

Это архитектурные выводы для обсуждения. Пошаговый план реализации будет составлен после замечаний.
