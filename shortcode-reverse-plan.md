# План выборочного обратного преобразования текстовых шорткодов

Дата: 2026-11-15.
Статус: реализовано и проверено в изолированном окружении. Результаты и границы проверки — в [отчёте](shortcode-reverse-verification.md). Применение к рабочей БД и поставка отдельно.

Основание: [анализ с замечаниями](shortcode-reverse-analysis.md). Цитаты пользователя в анализе сохранены без изменений. При расхождении с первоначальными рекомендациями анализа этот план следует замечаниям пользователя.

## 1. Принятые решения и границы

1. Политикой прямой и обратной подстановки владеет модуль шорткодов. Jodit получает определения через API и реализует общий алгоритм без конкретных имён в своём исходном коде.
2. Файловый менеджер возвращает полноценные публичные URL. `explorer.ts` и ядро файлового менеджера ради шорткодов не изменяются.
3. Определение из БД полностью переопределяет одноимённое программное определение, включая значение, тип, описание, пример и разрешение обратной замены. Выключенный в БД reverse не наследуется из кода.
4. Значение текстового шорткода — готовый результат. Прямое раскрытие выполняется одним проходом, без вложенности и каскадных замен.
5. Обратная замена выполняется в браузере. На сервере не вводятся преобразования контента перед сохранением или после чтения из БД. Исходник и отправляемая textarea должны содержать одно и то же нормализованное значение после синхронизации редактора.
6. При включённой интеграции загрузка определений обязательна: ошибка API отображается явно, редактор блокируется до успешного повтора загрузки. Сохранение формы через штатный браузерный submit также блокируется, пока один из её редакторов ожидает определения или находится в состоянии ошибки.
7. Виджетные шорткоды не получают нового отображения и не участвуют в обратной замене. Их существующую регистрацию и выполнение необходимо сохранить.
8. Поддержка шорткодов при выводе контента остаётся ответственностью темы и программиста. Базовые представления модулей не изменяются, новых зависимостей контентных модулей не появляется.
9. Переезды между доменами, SQL-замены, дополнительные старые домены и миграция существующего контента не входят в работу.
10. Автоматическое определение доступности модуля шорткодов и изменение текущего `enableShortcodes = true` отложены. Если интеграция включена и её endpoint недоступен, действует явная ошибка из пункта 6. При явно выключенной интеграции новый механизм не запускается.
11. Комментарии пользователя не удаляются. Если пояснение существующего кода перестанет быть актуальным, рядом добавляется объяснение новой схемы с сохранением исходного комментария.

## 2. Архитектура единого реестра

### 2.1. Определение шорткода

В пакете `yii2-cms-shortcode` ввести неизменяемый объект `ShortcodeDefinition`, представляющий полное определение:

- имя;
- тип;
- строку замены;
- описание;
- пример;
- режим обратного преобразования;
- идентификатор записи БД, если определение управляется через админку.

Объект не содержит Yii ActiveRecord, HTML-атрибутов, настроек Jodit или функций обработки DOM. `ShortcodeItem` остаётся представлением для справочного интерфейса и строится из эффективного определения; самостоятельно источники не объединяет.

Ввести типизированный режим `ReverseMode` с двумя значениями: `none` и `url-prefix`. В БД хранить строковое поле `reverse_mode` с обязательным значением по умолчанию `none`.

### 2.2. Источники и приоритеты

`ShortcodeCatalog` сохраняет узкую ответственность: загрузка и кэширование записей БД.

Новый `ShortcodeRegistry` отвечает за программные определения, объединение источников и получение эффективного набора. Порядок наложения:

```text
Встроенные определения
        ↓
Программные регистрации модулей
        ↓
Определения из БД — наивысший приоритет
        ↓
Единый эффективный набор
```

Встроенные определения создаёт внутренний `BuiltinShortcodeDefinitions` в модуле шорткодов. Здесь находятся имена `%staticHost%`, `%frontendHost%`, `%homeUrl%` и вычисление их значений в контексте текущего приложения.

Начальные правила:

| Шорткод | Reverse |
|---|---|
| `%staticHost%` | `url-prefix` |
| `%frontendHost%` | `none` |
| `%homeUrl%` | `none` |

Для `%frontendHost%` обратная замена не включается автоматически: это отдельное разрешение, которое можно задать программно или переопределением в БД.

Повторная программная регистрация одного имени выбрасывает исключение, даже при совпадении значений. Встроенные имена также уникальны в программном слое. БД всегда остаётся верхним слоем независимо от времени runtime-регистрации. Удаление переопределения из БД снова открывает программное определение.

> Здесь получается неоднозначность, повторное программное определение должно вызывать ошибку. Нельзя чтобы кто угодно и где угодно переопределял что угодно, это сложно дебажить. Программные определения уникальны по имени шорткода, нельзя зарегистрировать программно уже существующий шорткод, это должно выбрасывать исключение. Программные шорткоды может переопределить только база данных

Совпадение имени в БД и коде разрешено. Две записи БД с одним именем запрещены существующим уникальным ограничением и проверкой формы. Нельзя одновременно получить два эффективных типа под одним именем: переопределяется всё определение целиком.

Серверный резолвер, API, список шорткодов и методы менеджера получают определения из этого реестра. Отдельные конкурирующие карты в менеджере и самостоятельное объединение в read model устраняются.

Реестр хранится в пределах запроса. В общий APCu-кэш не помещаются вычисленные для конкретного приложения встроенные значения или runtime-регистрации. При изменении регистрации сбрасываются производные карты; при CRUD в админке инвалидируются и каталог БД, и его снимок в реестре текущего запроса.

### 2.3. Менеджер как совместимый фасад

`ShortcodeManager` остаётся компонентом приложения и реализацией `ShortcodeTextResolver`, но делегирует хранение определений реестру.

Сохранить публичные точки входа:

- `registerText()`;
- `registerWidget()`;
- `loadTextShortcodes()`;
- `getTextShortcodes()`;
- `getWidgetShortcodes()`;
- `getTextReplacement()`;
- `getWidgetClass()`;
- `resolveText()`.

Добавить к текстовой регистрации необязательный типизированный режим reverse с умолчанием `none`. Существующие двухаргументные вызовы остаются действительными. Пакетный `loadTextShortcodes()` продолжает регистрировать обычные текстовые определения с выключенным reverse; для задания политики используется явная регистрация определения.

Программная регистрация не должна случайно наследовать reverse от предыдущего определения: новый объект задаёт его полностью.

### 2.4. DI: решение после проверки исходников Yii2

В `src/config/common.php` зарегистрировать `ShortcodeRegistry` и `ShortcodeManager` как ленивые singleton по их классам. Компонент `shortcode` оставить определённым через класс менеджера:

```php
'container' => [
    'singletons' => [
        ShortcodeRegistry::class => ShortcodeRegistry::class,
        ShortcodeManager::class => ShortcodeManager::class,
    ],
],
'components' => [
    'shortcode' => ['class' => ShortcodeManager::class],
],
```

Это иллюстрация схемы; в реализации сохранить `Module::components()` как существующий источник определения компонента, а не продублировать его литералом.

Почему схема работает:

1. `Application::preInit()` применяет конфигурацию контейнера до создания пользовательских компонентов.
2. `ServiceLocator::get()` передаёт определение компонента в `Yii::createObject()`.
3. `Yii::createObject(['class' => ShortcodeManager::class])` обращается к DI-контейнеру по классу.
4. `Container::get()` создаёт singleton при первом обращении и возвращает тот же объект при следующих обращениях.
5. Constructor injection получает этот же объект. Обратного вызова `Yii::$app->get('shortcode')` из определения класса нет, поэтому рекурсия не возникает.

Ручное создание объекта при подключении конфигурационного файла не требуется: менеджер и зависимости создаются лениво, когда приложение уже настроено. Готовый объект Yii2 также поддерживает, но ранняя инициализация при сборке конфига здесь не даёт преимуществ.

Проверенные основания: `yii2/base/Application.php`, `yii2/BaseYii.php`, `yii2/di/Container.php`, `yii2/di/ServiceLocator.php`. Рабочие примеры `container.singletons` в проекте: конфигурации модулей Tags и Upload.

Гарантия общего экземпляра действует внутри запроса и жизни контейнера. Регистрации, нужные API и frontend, должны выполняться в общей инициализации соответствующих запросов, а не только в коде формы. Не вводить общую серверную сессию для переноса runtime-объектов между запросами.

## 3. Этап 1 — определения, реестр и единая прямая подстановка

Затрагиваемый пакет: `yii2-cms-shortcode`.

1. Добавить `ShortcodeDefinition`, `ReverseMode`, поставщик встроенных определений и `ShortcodeRegistry`.
2. Настроить singleton-проводку по схеме выше.
3. Перевести менеджер на реестр, сохранить публичные методы.
4. Перевести `ShortcodeListReadModel` и `ShortcodeItem` на эффективные определения.
5. Убрать расхождение приоритетов между серверным рендером и списком для API.
6. Сохранить один проход `resolveText()`: подставленный результат повторно не раскрывается. На клиенте далее применить ту же семантику.
7. Для текстовых имён ввести согласованную проверку синтаксиса, поддерживаемого серверным резолвером: `%name%`, где имя содержит ASCII-буквы, цифры и подчёркивание. Существующие некорректные данные не переписывать автоматически; обнаруженные несовместимости явно сообщать.
8. Проверять отсутствие вложенных текстовых шорткодов в значениях при сохранении и регистрации: значение должно быть конечным. В клиенте и серверном резолвере всё равно сохранять однопроходный алгоритм.

Результат этапа: одинаковое эффективное определение доступно через компонент приложения, DI, API и серверный резолвер; БД полностью переопределяет код.

## 4. Этап 2 — хранение, форма управления и валидация reverse

Затрагиваемый пакет: `yii2-cms-shortcode`.

1. Добавить новую миграцию от `BaseMigration` для поля `reverse_mode`; прежнюю установочную миграцию не менять. Старые записи получают `none`.
2. Расширить сущность, форму, сервис управления и преобразование строк каталога в определения.
3. В форму добавить настройку «Обратное преобразование»: «Отключено» / «Префикс URL». Для виджетного типа допустимо только «Отключено»; серверная проверка обязательна независимо от поведения формы.
4. Исправить проверку уникальности: программное определение не мешает создать переопределение в БД; проверяются другие записи БД с учётом текущего ID.
5. При `url-prefix` разрешать только готовый абсолютный HTTP(S)-префикс без credentials, query и fragment. `/`, пустые значения и вложенные шорткоды недопустимы. Путь в префиксе разрешён.
6. Сравнивать обратимые определения всего эффективного набора. Одинаковые префиксы для разных имён считать ошибкой; разные по длине вложенные префиксы разрешать. Проверять одинаковость с учётом принятого алгоритма сопоставления URL, включая регистр хоста и стандартный порт.
7. При проверке формы сначала построить предполагаемый эффективный набор с новой записью. Не проверять её как дополнительное независимое правило рядом с программным определением того же имени.
8. Проверять программные определения теми же правилами. Конфликт, обнаруженный при построении набора для API, должен давать явную ошибку, а не произвольный выбор правила.
9. Изменить версию ключа кэша каталога из-за нового формата и сохранить теговую инвалидацию. Обеспечить обновление реестра после create/edit/remove в том же запросе.

Результат этапа: администратор может создать `%staticHost%` в БД, задать ему своё значение и выключить reverse; API и frontend одинаково используют это определение. Удаление записи возвращает встроенное определение.

## 5. Этап 3 — API и загрузка определений в браузер

Затрагиваются `yii2-cms-shortcode` и `yii2-cms-jodit`.

1. Сохранить существующий endpoint и поля элементов, добавить обязательное поле `reverse`:

```json
{
  "shortcode": "%staticHost%",
  "type": "text",
  "replacement": "https://files.yii2-cms.docker.localhost",
  "description": "",
  "example": "%staticHost%",
  "reverse": {"mode": "url-prefix"}
}
```

Для выключенного преобразования передавать `{"mode":"none"}`. Виджетные элементы также имеют `none`.

2. Обновить PHPDoc ответа, TypeScript-интерфейсы и проверку данных во время выполнения. Проверять форму ответа, типы полей, режимы и допустимость правил.
3. Отсутствие `reverse` у старого ответа трактовать как `none`. Неизвестный непустой режим или некорректную структуру нового правила считать явной ошибкой конфигурации/API: пользователь требует видимых ошибок, поэтому молчаливый пропуск из анализа заменяется этим решением.
4. Объединить одновременные запросы нескольких редакторов и пикера через кэш Promise. После ошибки удалять неуспешную запись, чтобы повторная загрузка выполняла новый запрос.
5. Кэшировать определения до перезагрузки страницы. Не добавлять polling или live-синхронизацию с изменениями в другой вкладке; после редактирования определений требуется обновить страницу с редактором.
6. Не смешивать запросы с разными параметрами доступа: ключ загрузки учитывает URL и нормализованный набор дополнительных заголовков. Заголовки не выводятся в сообщения ошибок или журналы.

Результат этапа: пикер и преобразование используют один проверенный набор данных, параллельные редакторы не создают дублирующие запросы, повтор после ошибки возможен.

## 6. Этап 4 — готовность, явная ошибка и блокировка

Затрагивается `yii2-cms-jodit`.

1. Ввести жизненный цикл интеграции: `loading`, `ready`, `error`, `destroyed`.
2. Пока набор загружается, блокировать изменение контента и вставки. Использовать штатный `setReadOnly()` с сохранением исходного состояния редактора и локальную панель состояния поверх его области. Отдельно перекрыть действия собственных контролов, если они не соблюдают readonly автоматически.
3. При ошибке API показывать устойчивое сообщение в области редактора с кнопкой повторной загрузки. Одного сообщения в console недостаточно. Редактор остаётся заблокированным; исходный контент не удаляется.
4. Для редактора, принадлежащего форме, добавить единый на форму перехват штатного события submit. При `loading` или `error` любого подключённого редактора отменять отправку и указывать проблемный редактор. После успешной загрузки пользователь отправляет форму повторно; скрытого автоматического submit не вводить.
5. Не отключать исходную textarea через `disabled`, чтобы она не исчезла из отправляемых полей. Штатный readonly редактора, заданный вызывающим кодом, после загрузки не снимать.
6. При успешной загрузке применить превью к текущему контенту и синхронизировать textarea и source/split. Обеспечить отсутствие рекурсивных change и искусственного шага undo от загрузки правил.
7. При уничтожении редактора удалить свои подписки и участие в блокировке формы. Общий запрос не отменять только из-за уничтожения одного из нескольких потребителей; его результат для уничтоженного экземпляра игнорировать.

Jodit 4.15.14 предоставляет `setReadOnly()` и событие `readonly`; source-плагин учитывает его. Блокировка сохранения относится к обычной отправке формы через браузер, включая Yii ActiveForm. Она не является серверной гарантией и не защищает от намеренного обхода через `form.submit()` или произвольный AJAX — таких скрытых серверных преобразований в задачу не добавляем.

## 7. Этап 5 — прямая и обратная обработка HTML

Затрагивается `yii2-cms-jodit`; конкретные имена шорткодов в коде алгоритма отсутствуют.

Разделить внутри интеграции загрузку/UI пикера, операции над значениями URL и адаптацию к событиям Jodit. Не вводить отдельный npm-пакет или новый внешний контракт ради этого механизма.

### 7.1. Понятное объяснение существующих меток

В БД хранится:

```html
<img src="%staticHost%/a.jpg">
```

Для отображения плагин временно делает DOM примерно таким:

```html
<img src="https://files.example.com/a.jpg"
     data-jodit-shortcode-src="%staticHost%/a.jpg">
```

Метка запоминает исходное значение. При получении HTML для исходника и textarea она удаляется, а `src` снова становится `%staticHost%/a.jpg`.

Если пользователь заменил картинку на `b.jpg`, нельзя вернуть старое `a.jpg` из метки. Сначала нужно убедиться, что текущее значение всё ещё соответствует старому превью. Если адрес изменился, старая метка отбрасывается, а новый адрес отдельно проверяется на разрешённую обратную замену.

Именно поэтому восстановление ранее введённого шорткода и создание шорткода из нового URL — две разные операции. Это позволяет сохранять авторский выбор и не отменять правки пользователя.

### 7.2. Правила обработки

1. Для прямой подстановки использовать один проход: заменять исходные токены, не обрабатывать повторно результат подстановки.
2. Поддержать согласованно `src`, `href`, `poster` и `srcset`; `srcset` обрабатывать отдельным парсером списка URL и дескрипторов, а не `split(',')`. Не повреждать `data:` URL, даже если они не подходят ни под одно правило.
3. На выходе сначала восстановить неизменённые атрибуты из меток и удалить служебные метки. Затем применить reverse к новым или изменённым реальным URL.
4. Уже существующие токены сохранять без замены на другое имя, даже если значения совпадают. У шорткода с выключенным reverse продолжает работать прямое превью: запрещено только создание нового токена из полного URL.
5. Для каждого URL выбирать самый длинный подходящий разрешённый префикс. Выполнять одну обратную замену, без повторного применения правил к результату.
6. Проверять схему, host/port и границы пути. Не принимать чужой домен с похожим началом и не заменять `/media` внутри `/media-old`.
7. URL-парсер использовать для проверки компонентов, а не для безусловной пересериализации всего адреса. Сохранять исходный остаток пути, кодирование, query и fragment. Завершающий слеш префикса учитывать согласованно с прямым раскрытием; не удалять его молча из значения определения.
8. Не менять текстовые узлы, обычный текст статьи, CSS, скрипты и текстовый синтаксис виджетных шорткодов. Логика применяется к поддерживаемым HTML-атрибутам.
9. Преобразование HTML выполнять в инертном DOM. Не заменять живое дерево редактора при каждом чтении значения: это может потерять курсор и выделение. Возвращать исходную строку без повторной сериализации, если изменений нет.
10. Устранить ранний выход `restore()` только по отсутствию меток: у вставленного проводником полного URL меток ещё нет, но reverse всё равно должен работать.
11. Обеспечить идемпотентность: повторное чтение, переключение режима и сохранение не создают дополнительные токены или вложенные замены.

### 7.3. История и исходник

Jodit хранит историю как снимки живого DOM, где могут находиться реальные адреса и временные метки. Поэтому корректного HTML на выходе недостаточно: после Ctrl+Z/Ctrl+Y необходимо получить ту же картинку в WYSIWYG и тот же шорткод в исходнике.

Проверить и согласовать:

- вставку файла как одного пользовательского действия;
- замену изображения или ссылки через диалог;
- возврат DOM из истории;
- переключения WYSIWYG/source/split;
- загрузку правил после создания редактора;
- редактирование полного URL непосредственно в source.

После завершённой синхронизации нормализованный source должен совпадать с отправляемой textarea. Не допускать ситуации, когда в видимом исходнике остаётся домен, а скрыто отправляется другое значение. Учитывать внутреннюю блокировку source-плагина при его передаче значения в WYSIWYG и обновлять зеркало в согласованной точке без циклических change.

## 8. Этап 6 — проверки

Проверки должны подтверждать поведение и границы компонентов, а не повторять их внутреннюю реализацию.

### Серверная часть

- Компонент приложения и constructor injection возвращают один менеджер при любом порядке первого обращения; создание не вызывает рекурсии.
- Регистрация через компонент видна API/read model и серверному резолверу внутри запроса.
- Запись БД полностью переопределяет код, в том числе выключает reverse. Удаление возвращает программное определение.
- Однопроходное раскрытие не запускает повторную подстановку.
- Работают create/edit/remove с новым полем и инвалидацией кэша, а существующая виджетная регистрация сохраняется.
- Конфликты reverse, некорректные значения и некорректные имена дают понятные ошибки.
- Новая миграция применяется через штатный модульный механизм и корректно откатывается; существующие данные не переписываются.

### Преобразование URL и HTML

| Сценарий | Ожидаемый результат |
|---|---|
| Изображение со статического домена | Реальная картинка в WYSIWYG, токен в source и textarea |
| Обычный файл в `href` | Токен в адресе ссылки на выходе |
| `%homeUrl%` со значением `/` | Автоматических замен слешей нет |
| Переопределение из БД выключает reverse | Новый полный URL остаётся полным |
| Ранее введённый токен с выключенным reverse | Токен сохраняется, прямое превью работает |
| Похожий чужой домен или соседний путь | Подстановки нет |
| Несколько вложенных префиксов | Выбран самый длинный |
| URL с кириллицей, `%20`, query и fragment | Остаток адреса не изменяется |
| `srcset` с несколькими кандидатами и `data:` | Адреса и дескрипторы не повреждаются |
| Замена `a.jpg` на `b.jpg` | Старая метка не возвращает `a.jpg` |
| Повторная сериализация | Результат не меняется |

### Интеграция Jodit и формы

- Вставка из проводника, paste и ручное редактирование адресов.
- Source, WYSIWYG, split, undo/redo и диалоги ссылок/изображений.
- Исходное открытие во всех режимах, включая замедленную загрузку API.
- Ошибки HTTP и структуры ответа: явное сообщение, блокировка редактирования и штатного submit, успешный повтор.
- Несколько редакторов одной формы: блокировка снимается только после готовности всех; редакторы других форм не мешают отправке.
- Уничтожение редактора во время запроса, сохранение исходного readonly.
- Явное выключение интеграции: редактор работает без загрузки и преобразований шорткодов.
- Включённая интеграция без endpoint: видимая ошибка; автоматическую проверку установки модуля не добавляем.
- После отправки и повторного открытия нормализованный исходник соответствует сохранённому контенту.

Запустить PHP-проверки и миграционные сценарии в доступном окружении проекта, TypeScript `type-check`, сборку esbuild и браузерные сценарии для фактически установленной версии Jodit. Если требуемое окружение недоступно, явно указать непроверенные сценарии, не объявляя их пройденными.

## 9. Этап 7 — сборка, документация и поставка

1. Пересобрать `yii2-cms-jodit/dist` штатным ESBuild после успешных проверок исходников.
2. Обновить README модуля шорткодов: источники, приоритет БД, регистрация reverse, ограничения URL и однопроходная семантика.
3. Обновить README Jodit: атрибуты, исходник/textarea, обязательная загрузка, ошибка и повтор, границы блокировки submit, отсутствие преобразований на сервере.
4. Зафиксировать порядок совместимого обновления: миграция и серверная поддержка поля/API, затем новый бандл редактора. Старый клиент игнорирует добавочное поле; новый клиент воспринимает старый ответ без `reverse` как выключенное преобразование.
5. Проверить итоговые diff обоих отдельных репозиториев и сохранность комментариев. Коммиты, теги, push и применение к рабочей БД не входят в подготовку плана и потребуют дальнейших указаний по поставке.

## 10. Критерии завершения

- Пример `%staticHost%/origin/Blog/502/123.jpg` получается автоматически после вставки файла и виден в исходнике именно в том виде, который отправляется в БД.
- WYSIWYG показывает доступный файл по реальному URL, изменения ссылки и undo/redo не теряют пользовательские правки.
- Набор reverse задаётся только модулем шорткодов и его админкой; Jodit не содержит конкретных имён.
- БД имеет полный приоритет над программными определениями; все потребители получают согласованные значения.
- Нет каскадного раскрытия, серверных преобразований перед сохранением, изменений тем и зависимостей контентных модулей.
- Ошибки API явные и не оставляют включённую интеграцию незаметно работающей без правил.
- Выполнены применимые проверки; ограничения непроверенного окружения перечислены отдельно.
